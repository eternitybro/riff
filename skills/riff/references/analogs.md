# Finding analogs

An analog is useful because the interaction matches, not because its product is popular or looks polished.

Start with the user's named references and software solving the same job. Then remove the domain nouns and look for the same choice elsewhere. For example, "choose one generated illustration to keep" becomes "compare similar alternatives and commit to one." Photo selection, seat selection, and delivery-window selection are possible research directions, not claims that those interfaces behave identically.

Use the seven dimensions in [proof.md](proof.md). Keep the relevant matches and describe the limits. An interface optimized for frequent expert use may transfer poorly to an occasional user even if its layout is attractive.

For each candidate, record:

- The interaction being borrowed.
- The product UI or primary documentation inspected, with a link and inspection date.
- The correspondence check and its "same because" and "different because" lines.
- Any behavior that could not be verified.

Do not invent a feature, cite a search snippet as direct observation, or use remembered details as checked evidence. Research can suggest an idea without proving that it will work for this product. Present cross-category examples together with other useful analogs rather than forcing a separate presentation category.
